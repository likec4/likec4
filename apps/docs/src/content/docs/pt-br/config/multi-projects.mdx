Às vezes, você pode querer dividir seu modelo LikeC4 em vários modelos, com base em domínios, equipes ou qualquer outro critério.

Você pode fazer isso criando vários projetos no seu workspace e vinculando-os entre si.  
Também pode usar esse recurso para compartilhar seu modelo com outras equipes ou projetos.

Crie arquivos `likec4.config.json` nas pastas que você deseja transformar em projetos:

<FileTree>
- cloud
  - **likec4.config.json**
  - service1.c4
  - service2.c4
  - ...
- externals
  - **likec4.config.json**
  - amazon.c4
  - ...
</FileTree>

O LikeC4 encontra os projetos percorrendo o workspace (a pasta aberta no editor ou o caminho passado à CLI) em busca de [arquivos de configuração](/pt-br/config/#arquivo-de-configuração), ignorando pastas como `node_modules` e `.git`.  
Cada arquivo de configuração define um projeto na sua pasta.  
Um arquivo-fonte pertence ao projeto com a pasta mais próxima.  
Arquivos fora de qualquer pasta de projeto, e não incluídos por nenhum projeto, pertencem ao projeto `default`.

Os projetos podem ser aninhados.  
Nesse caso, os arquivos do projeto aninhado não fazem parte do projeto pai.

<FileTree>
- cloud
  - likec4.config.json
  - service1.c4
  - service2.c4
  - nested
    - likec4.config.json
    - service3.c4 // fará parte do projeto 'nested', não do projeto 'cloud'
</FileTree>

## Importar elementos

Você pode importar elementos de outros projetos usando a palavra-chave `import`.

```likec4
import { serviceA } from 'projectA'

model {
  serviceB = service {
    -> serviceA.api 'calls serviceA'
  }
}
```

O nome depois de `from` é o `name` de um projeto do mesmo workspace.
Para importar um projeto com outro nome, ou um projeto fora do workspace, declare-o em [`dependencies`](#dependências).

<Aside type='caution' title="Limitações">
No momento, aplicam-se as seguintes limitações:
- Sem `dependencies`, os projetos referenciados devem estar carregados no mesmo workspace
- Apenas elementos de **model** no nível superior podem ser importados. Os elementos aninhados ficam acessíveis por meio deles
</Aside>

## Dependências

<Aside type='caution' title="Experimental">
A seção `dependencies` é experimental. O formato dela pode mudar antes de se tornar estável.
</Aside>

Declare os projetos dos quais você importa na seção `dependencies` da configuração do projeto.
Cada entrada associa um nome de importação à pasta do projeto de dependência (a pasta com o arquivo de configuração dele).
O caminho é relativo à pasta do arquivo de configuração.

<FileTree>
- platform-model
  - likec4.config.json // "name": "platform"
  - auth.c4
- workspace
  - billing-service
    - likec4.config.json // "name": "billing-core"
    - billing.c4
  - checkout
    - **likec4.config.json**
    - checkout.c4
</FileTree>

```json title="workspace/checkout/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "checkout",
  "dependencies": {
    "billing": "../billing-service",
    "platform": "../../platform-model"
  }
}
```

As dependências definem os elementos a importar:

```likec4 title="workspace/billing-service/billing.c4"
specification {
  element service
}

model {
  invoices = service 'Invoices'
}
```

```likec4 title="platform-model/auth.c4"
specification {
  element service
}

model {
  auth = service 'Auth' {
    tokens = service 'Tokens'
  }
}
```

Os arquivos `.c4` do projeto usam o nome de importação, não o caminho:

```likec4 title="workspace/checkout/checkout.c4"
import { invoices } from 'billing'
import { auth } from 'platform'

specification {
  element system
}

model {
  checkout = system 'Checkout' {
    -> invoices 'creates invoices'
    -> auth.tokens 'validates tokens'
  }
}

views {
  view index {
    include *
  }
}
```

Um nome de importação segue as regras do [nome do projeto](/pt-br/config/#nome-do-projeto): não pode ser `default` e não pode conter `.`, `@` ou `#`.  
O nome de importação não precisa coincidir com o `name` da dependência.  
Os caminhos devem ser relativos: caminhos absolutos, letras de unidade e URLs não são permitidos.

O LikeC4 resolve `import ... from 'name'` assim:

1. Se o projeto declara `name` em `dependencies`, a entrada tem prioridade, mesmo que o workspace tenha um projeto com esse nome.
   Se o LikeC4 não encontra nenhum projeto na pasta da entrada, a importação falha com `Imported project not found`.
2. Caso contrário, o LikeC4 procura um projeto do workspace com esse `name`, como sem `dependencies`.

Um projeto não pode importar a si mesmo.
Uma entrada que aponta para a pasta do próprio projeto, ou um nome de importação igual ao nome do projeto, é um erro.

É preciso um arquivo de configuração para declarar `dependencies`: os arquivos do projeto `default` só podem importar projetos do workspace pelo nome.

### Projetos no workspace

Se o caminho aponta para a pasta de um projeto do workspace, a importação usa esse projeto, com todas as configurações dele.

### Projetos fora do workspace

Se o caminho aponta para uma pasta fora do workspace (a pasta aberta no editor ou o caminho passado à CLI), o LikeC4 a carrega apenas como fonte de elementos para importar:

- Ele lê os arquivos `.c4` e `.likec4` da pasta e das subpastas, exceto os arquivos que correspondem aos padrões de `exclude` da dependência.
- Ele lê apenas uma configuração JSON (`likec4.config.json`, `.likec4.config.json` ou `.likec4rc`).
  Uma configuração TypeScript ou JavaScript não é executada.
  Sem uma configuração JSON, são usadas as configurações padrão, e o nome da dependência é o nome da pasta dela.
- O `include` da dependência é ignorado.
- Ela não é um projeto do workspace: o LikeC4 não relata erros nos arquivos dela e não gera as visões dela.
- Vários projetos do workspace podem depender da mesma pasta.

Os arquivos fora do workspace não são observados.
Depois de alterá-los, execute **LikeC4: Reload projects** no VS Code ou reinicie a CLI.

Uma pasta dentro do workspace, dentro da pasta de um projeto ou dentro dos caminhos de `include` de um projeto não é carregada como dependência fora do workspace.
Se ela não for a pasta de um projeto do workspace, a importação falha com `Imported project not found`.
Uma pasta que contém o workspace também é ignorada.

### Limitações

- Uma dependência é um caminho para uma pasta local.
- As dependências não são transitivas: as `dependencies` de uma dependência são ignoradas, e só os elementos da própria dependência podem ser importados, não os elementos que ela importa.
- Não declare pastas de dependências aninhadas umas nas outras.
- O autocompletar em `from '...'` não sugere os nomes de importação de `dependencies`.

## Compartilhar especificação

Você pode compartilhar arquivos de especificação (ou qualquer outra fonte LikeC4) entre vários projetos usando a opção de configuração `include`.

### Usando caminhos de inclusão

Adicione uma configuração `include` ao seu projeto para incluir arquivos de diretórios fora da pasta do projeto:

<FileTree>
- shared
  - specs.c4
  - common-styles.c4
- cloud
  - likec4.config.json
  - services.c4
  - ...
- externals
  - likec4.config.json
  - amazon.c4
  - ...
</FileTree>

Os projetos `cloud` e `externals` podem incluir a especificação compartilhada:

```json title="cloud/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "cloud",
  "include": {
    "paths": ["../shared"]
  }
}
```

```json title="externals/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "externals",
  "include": {
    "paths": ["../shared"]
  }
}
```

Os caminhos são relativos à pasta do projeto.  
Para `maxDepth`, `fileThreshold` e as regras dos caminhos, veja [Incluir diretórios adicionais](/pt-br/config/#incluir-diretórios-adicionais).

### Usando links simbólicos (alternativa)

Como alternativa, você pode usar links simbólicos para compartilhar arquivos:

<FileTree>
- shared
  - specs.c4
- cloud
  - specs.c4 // -> ../shared/specs.c4
  - likec4.config.json
  - ...
- externals
  - specs.c4 // -> ../shared/specs.c4
  - likec4.config.json
  - ...
</FileTree>

<Aside type='note'>
Em geral, a configuração `include` é preferível a links simbólicos, pois é mais portável e mais fácil de gerenciar.
</Aside>
