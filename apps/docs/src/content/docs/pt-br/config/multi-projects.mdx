Às vezes, você pode querer dividir seu modelo LikeC4 em vários modelos, com base em domínios, equipes ou qualquer outro critério.

Você pode fazer isso criando vários projetos no seu workspace e vinculando-os entre si.  
Também pode usar esse recurso para compartilhar seu modelo com outras equipes ou projetos.

Crie arquivos `likec4.config.json` nas pastas que você deseja transformar em projetos:

<FileTree>
- cloud
  - **likec4.config.json**
  - service1.c4
  - service2.c4
  - ...
- externals
  - **likec4.config.json**
  - amazon.c4
  - ...
</FileTree>

O LikeC4 encontra os projetos percorrendo o workspace (a pasta aberta no editor ou o caminho passado à CLI) em busca de [arquivos de configuração](/pt-br/config/#arquivo-de-configuração), ignorando pastas como `node_modules` e `.git`.  
Cada arquivo de configuração define um projeto na sua pasta.  
Um arquivo-fonte pertence ao projeto com a pasta mais próxima.  
Arquivos fora de qualquer pasta de projeto, e não incluídos por nenhum projeto, pertencem ao projeto `default`.

Os projetos podem ser aninhados.  
Nesse caso, os arquivos do projeto aninhado não fazem parte do projeto pai.

<FileTree>
- cloud
  - likec4.config.json
  - service1.c4
  - service2.c4
  - nested
    - likec4.config.json
    - service3.c4 // fará parte do projeto 'nested', não do projeto 'cloud'
</FileTree>

## Importar elementos

Você pode importar elementos de outros projetos usando a palavra-chave `import`.

```likec4
import { serviceA } from 'projectA'

model {
  serviceB = service {
    -> serviceA.api 'calls serviceA'
  }
}
```

O nome depois de `from` é o `name` de um projeto do mesmo workspace.
Para importar um projeto com outro nome, ou um projeto fora do workspace, declare-o em [`dependencies`](#dependências).

<Aside type='caution' title="Limitações">
No momento, aplicam-se as seguintes limitações:
- Sem `dependencies`, os projetos referenciados devem estar carregados no mesmo workspace
- Apenas elementos de **model** no nível superior podem ser importados. Os elementos aninhados ficam acessíveis por meio deles
</Aside>

## Dependências

<Aside type='caution' title="Experimental">
A seção `dependencies` é experimental. O formato dela pode mudar antes de se tornar estável.
</Aside>

Declare os projetos dos quais você importa na seção `dependencies` da configuração do projeto.
Cada entrada associa um nome de importação ao projeto de dependência:

- um caminho para a pasta do projeto (a pasta com o arquivo de configuração dele), relativo à pasta do arquivo de configuração;
- uma [fonte git](#dependências-do-git): uma pasta de um repositório git em uma branch, uma tag ou um commit.

<FileTree>
- platform-model
  - likec4.config.json // "name": "platform"
  - auth.c4
- workspace
  - billing-service
    - likec4.config.json // "name": "billing-core"
    - billing.c4
  - checkout
    - **likec4.config.json**
    - checkout.c4
</FileTree>

```json title="workspace/checkout/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "checkout",
  "dependencies": {
    "billing": "../billing-service",
    "platform": "../../platform-model"
  }
}
```

As dependências definem os elementos a importar:

```likec4 title="workspace/billing-service/billing.c4"
specification {
  element service
}

model {
  invoices = service 'Invoices'
}
```

```likec4 title="platform-model/auth.c4"
specification {
  element service
}

model {
  auth = service 'Auth' {
    tokens = service 'Tokens'
  }
}
```

Os arquivos `.c4` do projeto usam o nome de importação, não o caminho:

```likec4 title="workspace/checkout/checkout.c4"
import { invoices } from 'billing'
import { auth } from 'platform'

specification {
  element system
}

model {
  checkout = system 'Checkout' {
    -> invoices 'creates invoices'
    -> auth.tokens 'validates tokens'
  }
}

views {
  view index {
    include *
  }
}
```

Um nome de importação segue as regras do [nome do projeto](/pt-br/config/#nome-do-projeto): não pode ser `default` e não pode conter `.`, `@` ou `#`.  
O nome de importação não precisa coincidir com o `name` da dependência.  
Um caminho local deve ser relativo: caminhos absolutos, letras de unidade e URLs não são permitidos.

O LikeC4 resolve `import ... from 'name'` assim:

1. Se o projeto declara `name` em `dependencies`, a entrada tem prioridade, mesmo que o workspace tenha um projeto com esse nome.
   Se o LikeC4 não encontra nenhum projeto na pasta da entrada, a importação falha com `Imported project not found`.
2. Caso contrário, o LikeC4 procura um projeto do workspace com esse `name`, como sem `dependencies`.

Um projeto não pode importar a si mesmo.
Uma entrada que aponta para a pasta do próprio projeto, ou um nome de importação igual ao nome do projeto, é um erro.

É preciso um arquivo de configuração para declarar `dependencies`: os arquivos do projeto `default` só podem importar projetos do workspace pelo nome.

### Projetos no workspace

Se o caminho aponta para a pasta de um projeto do workspace, a importação usa esse projeto, com todas as configurações dele.

### Projetos fora do workspace

Se o caminho aponta para uma pasta fora do workspace (a pasta aberta no editor ou o caminho passado à CLI), o LikeC4 a carrega apenas como fonte de elementos para importar:

- Ele lê os arquivos `.c4` e `.likec4` da pasta e das subpastas, exceto os arquivos que correspondem aos padrões de `exclude` da dependência.
- Ele lê apenas uma configuração JSON (`likec4.config.json`, `.likec4.config.json` ou `.likec4rc`).
  Uma configuração TypeScript ou JavaScript não é executada.
  Sem uma configuração JSON, são usadas as configurações padrão, e o nome da dependência é o nome da pasta dela.
- O `include` da dependência é ignorado.
- Ela não é um projeto do workspace: o LikeC4 não relata erros nos arquivos dela e não gera as visões dela.
- Vários projetos do workspace podem depender da mesma pasta.

Os arquivos fora do workspace não são observados.
Depois de alterá-los, execute **LikeC4: Reload projects** no VS Code ou reinicie a CLI.

Uma pasta dentro do workspace, dentro da pasta de um projeto ou dentro dos caminhos de `include` de um projeto não é carregada como dependência fora do workspace.
Se ela não for a pasta de um projeto do workspace, a importação falha com `Imported project not found`.
Uma pasta que contém o workspace também é ignorada.

### Dependências do git

Uma dependência pode vir de um repositório git.
Em vez de um caminho, informe um objeto com a URL do repositório, uma ref e, opcionalmente, a pasta do projeto no repositório:

```json title="checkout/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "checkout",
  "dependencies": {
    "billing": {
      "git": "https://github.com/my-org/billing.git",
      "ref": "v1.2.0",
      "path": "architecture"
    }
  }
}
```

| Campo  | Descrição |
| ------ | --------- |
| `git`  | URL do repositório: `https://host/org/repo.git`, `ssh://[user@]host[:port]/org/repo.git` ou `git@host:org/repo.git` |
| `ref`  | Obrigatório. Uma branch, uma tag ou o SHA de um commit |
| `path` | Pasta do projeto de dependência (a pasta com o arquivo de configuração dele), relativa à raiz do repositório. A raiz do repositório, se omitido |

- Outras formas de URL (`http://`, `file://`, `git://`, `ext::`, caminhos locais) são rejeitadas.
- URLs com senha ou token são rejeitadas. Use um credential helper do git ou chaves SSH.
- `path` deve ser relativo e não pode conter `..`.
- Outros campos são rejeitados.

Importe de uma dependência do git da mesma forma que de uma dependência local:

```likec4 title="checkout/checkout.c4"
import { invoices } from 'billing'

specification {
  element system
}

model {
  checkout = system 'Checkout' {
    -> invoices 'creates invoices'
  }
}

views {
  view index {
    include *
  }
}
```

#### Instalação

O LikeC4 não baixa dependências ao carregar o workspace.
Execute primeiro [`likec4 install`](/pt-br/tooling/cli/#dependências-do-git) no workspace e depois gere o site como de costume:

```sh
likec4 install
likec4 build
```

Enquanto uma dependência do git não estiver instalada:

- `likec4 build`, `likec4 export`, `likec4 gen`, `likec4 validate`, `likec4 sync leanix`, `likec4 diff`, `likec4 safe-delete` e `likec4 publish` falham.
  Com `--project`, apenas as dependências desse projeto são verificadas.
- `likec4 start`, `likec4 mcp` e o [plugin do Vite](/pt-br/tooling/vite-plugin/) continuam em execução e relatam o erro no modelo.
- No editor, a importação relata `Dependency 'billing' is not installed`, com a correção rápida **Install dependency 'billing'**.
  Os nomes importados também relatam erros `Could not resolve reference` até a dependência ser instalada.

`likec4 validate` relata o erro da importação, os outros comandos listam as dependências a instalar:

```
Dependency is not installed:
  - 'billing' of project 'checkout' (https://github.com/my-org/billing.git#v1.2.0:architecture)
Run `likec4 install` to install it.
```

Apenas `likec4 install` e `likec4 update` (e os comandos de instalação do editor) baixam dependências.

#### Versões

A primeira instalação resolve a `ref` para um commit e o guarda no [cache](#cache).
As instalações seguintes usam esse commit, mesmo que a branch ou a tag tenha mudado.
Para passar ao commit atual da ref, execute [`likec4 update`](/pt-br/tooling/cli/#dependências-do-git).

Projetos que usam o mesmo repositório e a mesma ref recebem o mesmo commit.
Versões diferentes de um repositório podem ser usadas lado a lado: em projetos diferentes do workspace ou em um projeto com nomes de importação diferentes:

```json title="checkout/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "checkout",
  "dependencies": {
    "billing-v1": {
      "git": "https://github.com/my-org/billing.git",
      "ref": "v1.2.0",
      "path": "architecture"
    },
    "billing": {
      "git": "https://github.com/my-org/billing.git",
      "ref": "v2.0.0",
      "path": "architecture"
    }
  }
}
```

Não há arquivo de lock: os commits ficam guardados no cache de cada máquina.
O build é reproduzível em uma máquina, mas outra máquina (ou uma execução de CI com o cache vazio) resolve as refs novamente.
Use uma tag ou o SHA de um commit como `ref` para obter o mesmo modelo em todos os lugares.

#### O que é baixado

O LikeC4 baixa a pasta `path` do repositório no commit e mantém apenas:

- arquivos `.c4` e `.likec4`, em qualquer profundidade;
- a configuração JSON (`likec4.config.json`, `.likec4.config.json` ou `.likec4rc`) na pasta `path`.

Uma configuração TypeScript ou JavaScript da dependência não é executada, e o `include` da dependência é ignorado.
Como um [projeto fora do workspace](#projetos-fora-do-workspace), uma dependência do git é apenas uma fonte de elementos para importar.
Se os arquivos dela tiverem erros de sintaxe, a importação relata um aviso com o número desses arquivos.

#### Requisitos

- `git` 2.35.2 ou mais recente no `PATH`.
- Repositórios privados usam as credenciais e as chaves SSH que você configurou para o git.
  O LikeC4 nunca pede senha: o git é executado sem prompts, e uma instalação que precisa de entrada falha.
- Na CI, configure o acesso na configuração global do git, por exemplo com `git config --global url.<base>.insteadOf <url>` ou um credential helper.
  As variáveis de ambiente `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*` e `GIT_CONFIG_PARAMETERS` são ignoradas.

#### Cache

As dependências instaladas ficam na pasta `dependencies` do diretório de cache do LikeC4:

| Sistema | Diretório de cache |
| ------- | ------------------ |
| macOS   | `~/Library/Caches/likec4` |
| Linux   | `$XDG_CACHE_HOME/likec4` ou `~/.cache/likec4` |
| Windows | `%LOCALAPPDATA%\likec4\cache` |

A variável de ambiente `LIKEC4_CACHE_DIR` define outro diretório de cache.

A extensão do VS Code mantém o próprio cache no armazenamento da extensão.
Instale as dependências nele com o comando **LikeC4: Install git dependencies** ou com a correção rápida, e atualize-as com **LikeC4: Update git dependencies**.
A CLI e o VS Code não compartilham o cache: instale as dependências em cada um.
Outros editores que executam `likec4 lsp` usam o cache da CLI.

No VS Code, **Go to definition** em um elemento importado abre uma cópia somente leitura do arquivo da dependência.

#### API do modelo

[`LikeC4.fromWorkspace`](/pt-br/tooling/model-api/) também não baixa dependências.
Uma dependência que não está instalada é relatada em `getErrors()`, e `fromWorkspace` rejeita apenas com `throwIfInvalid: true`.

### Limitações

- As dependências não são transitivas: as `dependencies` de uma dependência são ignoradas, e só os elementos da própria dependência podem ser importados, não os elementos que ela importa.
- Não declare pastas de dependências aninhadas umas nas outras.
- O autocompletar em `from '...'` não sugere nomes de importação de `dependencies`.
- Um projeto não pode limitar quais dos seus elementos outros projetos importam.
- Uma dependência não pode compartilhar a especificação dela com os projetos que a importam, e `include` não pode apontar para um repositório git ([#2378](https://github.com/likec4/likec4/issues/2378)).
- Dependências do git não são suportadas no navegador: no playground e no vscode.dev.
  No vscode.dev, a importação relata `remote dependencies are not supported in this environment`.
- O git é a única forma de baixar uma dependência: não há download por HTTP simples, nem forma abreviada como `github:org/repo`, nem pacotes publicados como fonte.
- Imagens e descrições Markdown externas de uma dependência do git não estão disponíveis: imagens locais de ícones e arquivos Markdown da dependência não são baixados.
  [Ícones incluídos](/pt-br/dsl/styling/#ícones-incluídos) e ícones com URLs `https://` funcionam.
- Não há comando para limpar o cache.
- Um projeto não pode declarar a versão do LikeC4 de que precisa.
- Um nome de importação que não está declarado em `dependencies` sempre recorre aos projetos do workspace; essa busca não pode ser desativada.

## Compartilhar especificação

Você pode compartilhar arquivos de especificação (ou qualquer outra fonte LikeC4) entre vários projetos usando a opção de configuração `include`.

### Usando caminhos de inclusão

Adicione uma configuração `include` ao seu projeto para incluir arquivos de diretórios fora da pasta do projeto:

<FileTree>
- shared
  - specs.c4
  - common-styles.c4
- cloud
  - likec4.config.json
  - services.c4
  - ...
- externals
  - likec4.config.json
  - amazon.c4
  - ...
</FileTree>

Os projetos `cloud` e `externals` podem incluir a especificação compartilhada:

```json title="cloud/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "cloud",
  "include": {
    "paths": ["../shared"]
  }
}
```

```json title="externals/likec4.config.json"
{
  "$schema": "https://likec4.dev/schemas/config.json",
  "name": "externals",
  "include": {
    "paths": ["../shared"]
  }
}
```

Os caminhos são relativos à pasta do projeto.  
Para `maxDepth`, `fileThreshold` e as regras dos caminhos, veja [Incluir diretórios adicionais](/pt-br/config/#incluir-diretórios-adicionais).

### Usando links simbólicos (alternativa)

Como alternativa, você pode usar links simbólicos para compartilhar arquivos:

<FileTree>
- shared
  - specs.c4
- cloud
  - specs.c4 // -> ../shared/specs.c4
  - likec4.config.json
  - ...
- externals
  - specs.c4 // -> ../shared/specs.c4
  - likec4.config.json
  - ...
</FileTree>

<Aside type='note'>
Em geral, a configuração `include` é preferível a links simbólicos, pois é mais portável e mais fácil de gerenciar.
</Aside>
