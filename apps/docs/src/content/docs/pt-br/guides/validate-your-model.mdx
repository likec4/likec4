Encontre modelos quebrados antes do merge.
Uma verificação de CI tem três camadas:

1. **Validação**: erros de sintaxe e semânticos, e layouts manuais desatualizados. Use `likec4 validate`.
2. **Formatação**: os arquivos fonte seguem o formato padrão. Use `likec4 format --check`.
3. **Suas próprias regras**: restrições de arquitetura específicas do seu time. Escreva-as como testes com Vitest e a [API do modelo](/tooling/model-api/).

:::note
Consulte o repositório <a href="https://github.com/likec4/template" target='_blank'>likec4/template</a> para ver um exemplo completo.

## Validar o modelo

`likec4 validate` verifica no workspace:

- erros de sintaxe e semânticos
- layout drift: layouts manuais que não correspondem mais ao modelo

```sh
# Falha apenas com erros
npx likec4 validate

# Falha com erros e com qualquer aviso
npx likec4 validate --max-warnings 0
```

O comando termina com código `0` quando o modelo é válido.
Ele termina com código `1` quando há erros, ou mais avisos do que `--max-warnings` permite.
Sem `--max-warnings`, os avisos são exibidos, mas não fazem a verificação falhar.

Opções úteis:

| Opção              | O que faz                                                                  |
| ------------------ | -------------------------------------------------------------------------- |
| `--max-warnings N` | Falha quando há mais de `N` avisos. `0` falha com qualquer aviso           |
| `--no-layout`      | Ignora a verificação de layout drift                                       |
| `--file, -f`       | Reporta apenas erros e avisos destes arquivos (pode ser repetido)          |
| `--project, -p`    | Verifica o layout drift de um projeto em um workspace com vários projetos  |
| `--json`           | Exibe o resultado como JSON, para outras ferramentas lerem                 |

A saída JSON tem `valid`, `errors`, `warnings`, `maxWarnings` e `stats`.
Cada erro e aviso tem `message`, `file`, `line` e `range`.

Veja a [referência da CLI](/tooling/cli/#validate) para todas as opções.

## Verificar a formatação

`likec4 format --check` lista os arquivos que precisam de formatação.
Ele não os altera.

```sh
npx likec4 format --check
```

O comando termina com código `1` se algum arquivo precisar de formatação.
Execute `npx likec4 format` localmente para corrigi-los.

Use `--project` ou `--files` para verificar apenas parte do workspace.
Veja a [referência da CLI](/tooling/cli/#format).

## Escrever suas próprias regras

Algumas regras são específicas da sua arquitetura.
Por exemplo, "todo `app` tem uma tecnologia" ou "todo relacionamento tem um responsável".
Escreva-as como testes com o [Vitest](https://vitest.dev) e a [API do modelo](/tooling/model-api/).

### Exemplo

Este teste verifica que todo elemento do tipo `app` tem uma `technology`:

```ts
// test/metadata.spec.ts
import { LikeC4 } from 'likec4'
import { test } from 'vitest'

// Load the workspace and compute the model.
// The path is resolved from the folder where you run vitest.
const likec4 = await LikeC4.fromWorkspace('.')
const model = await likec4.computedModel()

// `test.for` generates a test per element,
// so each failure is reported separately
test.for(
  model
    // Select elements of kind `app`
    .elementsWhere({ kind: 'app' })
    // Map to [id, element] tuples, the id is used in the test name
    .map(e => [e.id, e] as const)
    .toArray(),
)('app "%s" has technology', ([, e], { expect }) => {
  expect(e.technology).toBeTruthy()
})

// Or use `expect.soft` to collect all failures in one test
test('elements of kind `app` have technology', ({ expect }) => {
  expect.hasAssertions()
  for (const app of model.elementsWhere({ kind: 'app' })) {
    expect.soft(app.technology, `app ${app.id} has no technology`).toBeTruthy()
  }
})
```

`elementsWhere` retorna um iterador.
Use `.toArray()` quando precisar de um array, ou percorra-o com `for...of`.
Veja a [referência da API do modelo](/tooling/model-api/reference/) para todos os métodos de consulta.

:::note
Carregar um workspace analisa todos os fontes, então leva tempo.
Carregue-o uma vez por arquivo de teste e reutilize a instância.
:::

### Pré-gerar o modelo

Os testes iniciam mais rápido com um modelo pré-gerado.
Gere-o uma vez no [global setup](https://vitest.dev/config/#globalsetup) do Vitest:

```ts
// global-setup.ts
import { execSync } from 'node:child_process'

export default function() {
  execSync('npx likec4 gen model -o ./test/likec4-model.ts', {
    stdio: 'inherit',
  })
}
```

O modelo gerado é tipado.
Você tem verificação de tipos e autocompletar nos testes:

```ts
// test/metadata.spec.ts
import { likec4model } from './likec4-model'
import { test } from 'vitest'

test('relationships have metadata', ({ expect }) => {
  expect.hasAssertions()
  for (const r of likec4model.relationships()) {
    expect.soft(
      r.getMetadata('key'), // type-checked key
      `Relationship ${r.source.id} -> ${r.target.id} has no metadata`,
    ).toBeDefined()
  }
})
```

### Compartilhar o modelo com uma fixture

Uma fixture de [contexto de teste](https://vitest.dev/api/#test-context) coloca o modelo em cada teste:

```ts
// test/likec4test.ts
import { likec4model } from './likec4-model'
import { test } from 'vitest'

interface LikeC4TestFixtures {
  likec4: typeof likec4model
}

// A test function with the model in its context
export const likec4test = test.extend<LikeC4TestFixtures>({
  likec4: async ({}, use) => {
    await use(likec4model)
  },
})
```

Use-a nos seus testes:

```ts
// test/metadata.spec.ts
import { likec4test } from './likec4test'

likec4test('relationships have metadata', ({ expect, likec4 }) => {
  expect.hasAssertions()
  for (const r of likec4.relationships()) {
    expect.soft(
      r.getMetadata('key'),
      `Relationship ${r.source.id} -> ${r.target.id} has no metadata`,
    ).toBeDefined()
  }
})
```

## Executar as verificações em pull requests

Este workflow do GitHub Actions executa as três verificações em cada pull request.
Ele espera `likec4` e `vitest` nas suas `devDependencies`.

```yaml
# .github/workflows/likec4.yml
name: LikeC4

on:
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: 22 # likec4 requires Node.js 22.23.3 or newer
          cache: npm

      - run: npm ci

      - name: Validate
        run: npx likec4 validate --max-warnings 0

      - name: Check formatting
        run: npx likec4 format --check

      - name: Architecture rules
        run: npx vitest run
```

Cada etapa faz o job falhar com um código de saída diferente de zero.
Outros sistemas de CI (GitLab CI, Azure Pipelines, Jenkins) executam os mesmos três comandos.
